# File-free materialization memory benchmark

Run on 2026-08-30 with CPython 3.14.2, DuckDB 1.5.5, macOS 26.6.2 arm64.
The harness is [`benchmarks/memory_materialization.py`](../memory_materialization.py).
It invokes the production `Interceptor.intercept` → `Store` path, including
structured-payload sizing, shape extraction, type inference, explicit DuckDB
DDL, insertion, envelope recording, and handle construction. No temporary
payload files are used.

Each scenario runs in a fresh child process. This is necessary because
`resource.getrusage(...).ru_maxrss` is a process high-water mark. The benchmark
creates one independently decoded payload per requested concurrent call, then
records the high-water mark before and after interception. `peak` is the
absolute process high-water mark; `increment` is `peak - baseline` and excludes
input construction. Both are reported because the baseline includes Python,
MCP, DuckDB, and retained decoded inputs. The current implementation completes
planning synchronously and serializes writes, so concurrency results measure
the current admission path rather than hypothetical overlapping planners.

two-call case in the matrix.

## Near-ceiling stress cases

These additional cases were run near the configured default because the
configured DuckDB setting is `1GB`. That setting is DuckDB's engine allocation
limit, not a process RSS or container-memory ceiling. The deployment assumption
used for the product decision below is a **1 GiB (1,073,741,824-byte) process
memory budget**; the host used for the run was not itself memory-constrained.

| shape / selected payload | concurrency | peak RSS | increment | elapsed |
| --- | ---: | ---: | ---: | ---: |
| flat / 24 MiB | 2 | 689.5 MiB (723,124,224 B) | 406.6 MiB (426,311,680 B) | 157.9 s |
| nested / 24 MiB | 2 | 763.5 MiB (800,636,928 B) | 389.5 MiB (408,371,200 B) | 106.2 s |
| wide / 24 MiB | 2 | 797.3 MiB (836,239,360 B) | 467.8 MiB (490,455,040 B) | 134.7 s |
| mixed / 24 MiB | 2 | 716.4 MiB (751,108,096 B) | 399.6 MiB (418,840,576 B) | 135.0 s |
| flat / 30 MiB | 1 | 732.1 MiB (767,934,464 B) | 473.9 MiB (496,861,184 B) | 98.0 s |
| flat / 30 MiB | 2 | 906.0 MiB (950,288,384 B) | 579.5 MiB (607,748,096 B) | 197.2 s |

## Recommendation

Do not raise either limit. With the 1 GiB process-memory assumption, retain
`max_concurrent_materializations = 2` and lower `max_payload_bytes` from 32 MiB
to **24 MiB**. The worst 24 MiB × 2 case (wide) reached 797.3 MiB, leaving about
226 MiB below the 1 GiB process budget. The flat 30 MiB × 2 case reached 906.0
MiB; linear interpolation to 32 MiB would leave little or no safety margin.
The default is now changed consistently in `src/sluice/config.py`,
`sluice.example.toml`, and spec §7. Deployments with a larger memory budget may
choose 32 MiB, but should rerun this harness on the target host first.

This is not an OOM guarantee: `structuredContent` has already been decoded by
the SDK before Sluice measures it, and `ru_maxrss` is a high-water mark rather
than current RSS. The result is evidence for a limit, not a portable bound.

## Reproduction

```bash
uv run python benchmarks/memory_materialization.py --all
uv run python benchmarks/memory_materialization.py --shape flat --target-mib 30 --concurrency 2
```

The full default matrix is 24 isolated scenarios (four shapes × three sizes ×
two concurrency settings). One-off choices also include 24/30 MiB and
concurrency 4 for longer stress runs.

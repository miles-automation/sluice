# File-free materialization memory benchmark

Run on 2026-08-30 with CPython 3.14.2, DuckDB 1.5.5, macOS 26.6.2 arm64.
The harness is [`benchmarks/memory_materialization.py`](../memory_materialization.py).
It invokes the production `Interceptor.intercept` → `Store` path, including
structured-payload sizing, shape extraction, type inference, explicit DuckDB
DDL, insertion, envelope recording, and handle construction. No temporary
payload files are used.

Each scenario runs in a fresh child process. This is necessary because
`resource.getrusage(...).ru_maxrss` is a process high-water mark. The benchmark
creates one independently decoded payload per requested concurrent call, then
records the high-water mark before and after interception. `peak` is the
absolute process high-water mark; `increment` is `peak - baseline` and excludes
input construction. These are high-water differences, not current-RSS readings
or a claim that each call allocates exactly that amount. The baseline includes
Python, MCP, DuckDB, and retained decoded inputs. The current implementation
completes planning synchronously and serializes writes; additionally, the
admission semaphore wraps `_build_plans`, not payload selection or commit.
Concurrency results therefore describe current behavior rather than proving a
whole-pipeline memory bound.

## Matrix results

Payloads are object envelopes with an `items` row array, sized to within one
row of the target. Values are MiB of selected structured payload. Numbers are
peak RSS in MiB (`absolute / increment multiple` in parentheses).

| --- | ---: | ---: | ---: |
| flat | 1 | 128.0 / 31.49× | 135.7 / 37.24× |
| flat | 4 | 189.5 / 18.09× | 219.5 / 24.07× |
| flat | 16 | 413.6 / 14.66× | 509.2 / 18.46× |
| nested | 1 | 126.5 / 28.03× | 139.4 / 34.98× |
| nested | 4 | 196.0 / 18.61× | 234.3 / 22.75× |
| nested | 16 | 430.1 / 14.27× | 535.9 / 15.08× |
| wide | 1 | 128.1 / 28.02× | 143.4 / 41.80× |
| wide | 4 | 208.8 / 19.55× | 237.1 / 25.00× |

The small-payload multiples are dominated by fixed interpreter/DuckDB startup
and are not useful for scaling. At 16 MiB, the one-call absolute peaks were
414–464 MiB and two-call peaks were 509–566 MiB. The wide shape has 64 scalar
fields plus padding and was the highest two-call case in the matrix, making it a
useful column-count stress shape rather than a claim that all real payloads
have this schema.

## Channel-mode results

The matrix above is structured-only. The same flat 4 MiB, one-call scenario was
then run through each supported channel mode. Text mode supplies JSON in one
text block; dual mode supplies the same JSON in both `structuredContent` and a
text block, exercising selection, parsing, conflict comparison, and retention
of both channels.

| mode | peak RSS | high-water increment | increment multiple |
| --- | ---: | ---: | ---: |
| structured | 198,721,536 B (189.5 MiB) | 75,890,688 B (72.4 MiB) | 18.09× |
| text | 234,782,720 B (223.9 MiB) | 112,115,712 B (106.9 MiB) | 26.73× |
| dual | 244,531,200 B (233.3 MiB) | 121,700,352 B (116.1 MiB) | 29.02× |

Dual-channel retention is therefore about 1.6× the structured-only high-water
increment in this representative case. Payload-size measurements that omit
dual mode cannot establish a safe process-memory ceiling.

## Long-session retention

A single process retained all tables and envelope rows for 15 sequential flat
4 MiB dual-channel calls. Table creation was validated after every call and the
final envelope count was 15. Each call used a fresh decoded payload object. The
process high-water increment reached 539,656,192 B (514.7 MiB) after call 15,
versus 125,599,744 B (119.8 MiB) after call 1. The high-water readings often
rose by roughly 25–50 MiB per later call, with plateaus between allocations;
this is session retention, not a per-call instantaneous RSS bound.

| call | peak RSS | high-water increment |
| ---: | ---: | ---: |
| 1 | 240.8 MiB | 119.8 MiB |
| 5 | 404.5 MiB | 283.6 MiB |
| 10 | 563.4 MiB | 442.4 MiB |
| 15 | 635.6 MiB | 514.7 MiB |

## Near-ceiling stress cases

These additional cases were run near the configured default because the
configured DuckDB setting is `1GB`. That setting is DuckDB's engine allocation
limit, not a process RSS or container-memory ceiling. The deployment assumption
used for the product decision below is a **1 GiB (1,073,741,824-byte) process
memory budget**; the host used for the run was not itself memory-constrained.

| shape / selected payload | concurrency | peak RSS | increment | elapsed |
| --- | ---: | ---: | ---: | ---: |
| flat / 24 MiB | 2 | 689.5 MiB (723,124,224 B) | 406.6 MiB (426,311,680 B) | 157.9 s |

## Pre-R11 recommendation and blocker

At the time of these pre-fix runs, the conclusion was: do not change either
configured default based on this benchmark. The earlier
24 MiB recommendation is withdrawn: even the 24 MiB structured-only cases omit
dual-channel retention and long-session accumulation, and the current admission
semaphore does not cover selection or commit. The 32 MiB default remains in
place but **untrusted** as a process-memory bound. This historical recommendation
is superseded by the post-R11 calibration below.

For a deployment with a 1 GiB (1,073,741,824-byte) process-memory budget, the
runtime-memory blocker (plan R11) must first define and enforce a whole-pipeline budget,
bound retained session state, and account for SDK structured-content decoding.
Only after that change should `max_payload_bytes` and
`max_concurrent_materializations` be re-sized. `duckdb_max_memory = "1GB"` is
DuckDB's engine allocation setting, not a process RSS or container-memory
ceiling. The host used here was not itself memory-constrained.
This is not an OOM guarantee: `structuredContent` has already been decoded by
the SDK before Sluice measures it, and `ru_maxrss` is a high-water mark rather
than current RSS. The result is evidence for a limit, not a portable bound.

## Post-blocker calibration (2026-08-31)

After the whole-pipeline admission and retained-session bounds landed, every
shape was rerun at 1 MiB, dual channel, concurrency 2. These fresh-process runs
exercise the most expensive channel mode and the configured concurrency.

| shape | elapsed | peak RSS | increment above decoded-input baseline |
| --- | ---: | ---: | ---: |
| flat | 8.30 s | 161,562,624 B | 57,769,984 B |
| nested | 5.76 s | 176,537,600 B | 66,928,640 B |
| wide | 7.64 s | 173,326,336 B | 65,830,912 B |
| mixed | 7.16 s | 165,625,856 B | 59,899,904 B |

A separate flat 1 MiB dual-channel run retained 15 sequential calls. Its
process high-water mark rose from 147,275,776 bytes after call 1 to 274,628,608
bytes after call 15 (168,148,992 bytes above baseline). This is evidence for the
separate logical retention budget, not a claim that RSS grows linearly.

The admission calculation now counts both structured and text channels, so an
input carrying 1 MiB in each channel exceeds this ceiling rather than being
treated as a 1 MiB payload.

This calibration changes the operational recommendation: the v0 default
`max_payload_bytes` is 1,048,576 bytes. The former 32 MiB default is not retained;
near-ceiling runs above show that it implied minute-scale materialization latency
and approached the reference 1 GiB process budget. The 1 MiB value remains an
admission/retention bound, not a guarantee about memory already consumed while
the MCP SDK decoded the downstream result.

## Reproduction

```bash
uv run python benchmarks/memory_materialization.py --all
uv run python benchmarks/memory_materialization.py --shape flat --target-mib 4 --concurrency 1 --mode structured
uv run python benchmarks/memory_materialization.py --shape flat --target-mib 4 --concurrency 1 --mode text
uv run python benchmarks/memory_materialization.py --shape flat --target-mib 4 --concurrency 1 --mode dual
uv run python benchmarks/memory_materialization.py --shape flat --target-mib 4 --sequential-calls 15 --mode dual
uv run python benchmarks/memory_materialization.py --shape flat --target-mib 30 --concurrency 2 --mode structured
```

The full default matrix is 24 isolated structured-only scenarios (four shapes ×
three sizes × two concurrency settings). Channel modes and sequential retention
are explicit one-off runs because their larger cases are intentionally costly.
